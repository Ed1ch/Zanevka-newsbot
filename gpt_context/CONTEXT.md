# zanevka newsbot Context

Краткий актуальный контекст для нового AI-сеанса. Это не журнал всех изменений.

## Что делает проект

zanevka newsbot обрабатывает общую партию EML с DOCX, изображениями и VK; после проверки полноты публикует новости либо откладывает всю партию на один запуск.

## Текущее состояние и ближайшая задача

- Python Newsbot реализован в корне репозитория; существующая логика обработки и публикации новостей остаётся самостоятельной.
- В feature/webui-api-batch-20261023 от пакетной базы 9280002 добавлены
  webui_server.py (Flask/Waitress), сессия/CSRF/login, запуск prelaunch отдельным
  процессом, настройки config.py с ревизией, Debug, cron-флажок и общий SSE.
- Лаунчер владеет .main.lock и .newsbot.running, активирует журнал до почты;
  после закрытия обычной чистой пустой проверки пишет метку. Очистка таких
  журналов самим ботом — от 600 секунд; пустой повтор с погашением флага остаётся.
- WebUI подключён к API без изменения основного HTML/CSS. Отдельная страница
  входа использует первую исходную тему; logout/Debug не имеют контролов.
  Рабочие настройки в localStorage не сохраняются, тема сохраняется.
- Проверки: probe/check_logging.py и probe/check_webui_api.py, опциональный
  браузерный стенд serve_webui_fixture.py/check_webui_browser.py. Все рабочие
  сервисы подменены. Живые HTTPS/cron/IMAP/VK/WP и Windows/FreeBSD здесь не проверены.
- Деплой, ручные API-команды и ограничения текущих подписей: webui/DEPLOYMENT.md,
  webui/README.md. Следующий UI-проход должен добавить logout/Debug и привести
  статические подписи расписания/сброса к серверной семантике.

## Реализация партии в feature/batch-integrity-20261022

Внешний запуск — `python prelaunch.py` или `prelaunch.main()`. Диспетчер
удерживает `flags/.main.lock` и вызывает один `main.py` с параметром
`defer_if_incomplete`; `integrity_check.py` возвращает отчёт полноты.
Старый CLI `python main.py` направляется через диспетчер. Копии конвейера нет.

Партия фиксируется при начальной проверке UNSEEN. Все письма скачиваются
и получают подтверждённый SEEN до публикации. Вложения объединяются,
повторное имя (без учёта регистра) даёт WARNING и исключение последующих
экземпляров до сопоставления. Границы текстов писем и приоритет VK из DOCX сохранены.

Первый неполный проход возвращает всем письмам UNSEEN, затем создаёт
`flags/delayed.publish`; временные EML/картинки удаляются. При следующем запуске
флаг погашается, всё скачивается заново и публикуется без второй отсрочки.
DOCX без картинок, но с VK, не задерживает партию. Без картинок и VK
используется существующий `s600xu_2x.webp`; без своих картинок и без
успешного VK preview соответствующая новость пропускается.

Технические ошибки подготовки останавливают партию без флага отсрочки;
ошибка новости в цикле публикации не прерывает следующие. Список партии
не сохраняется, отката почты нет; восстановление выполняет администратор.
Debug для сброса служебного состояния реализован только в API под общим lock, без восстановления почты.

Все служебные флаги и lock-файлы размещаются в `flags/` относительно папки
проекта. Каталог создаётся автоматически перед получением lock; runtime-файлы
исключены из Git. Это правило относится к `.newsbot.disabled`, running и меткам пустых журналов.

Для API-интеграции выполняются `python probe/check_logging.py` и
`python probe/check_webui_api.py`; check_batch.py не менялся и не запускался.
Проверено в Debian 13/Python 3.13; живые сервисы, Pandoc, Windows 10 и FreeBSD
требуют отдельной проверки при деплое.

## Текущий подход к разработке

- Git-репозиторий — source of truth.
- Разработка идёт небольшими проверяемыми изменениями.
- Перед заметным изменением: сначала анализ и план, затем код.
- AI не должен делать сопутствующий рефакторинг без явного запроса.
- После изменения: review diff, тест/ручная проверка, затем commit.

## Для AI

Перед правкой:
1. Прочитать `gpt_context/ARCHITECTURE.md` и `gpt_context/DECISIONS.md`; для WebUI также `webui/README.md` и `webui/AGENTS.md`.
2. Найти реально затронутые файлы и usages.
3. Если изменение затрагивает несколько модулей — сначала предложить план.
4. Сохранять решение достаточно простым, чтобы владелец проекта мог его поддерживать.
