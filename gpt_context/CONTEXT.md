# zanevka newsbot Context

Краткий актуальный контекст для нового AI-сеанса. Это не журнал всех изменений.

## Что делает проект

zanevka newsbot обрабатывает EML-письмо с DOCX и изображениями, собирает новости, обрабатывает связанные VK-материалы и публикует результат в WordPress.

## Текущее состояние и ближайшая задача

- Python Newsbot реализован в корне репозитория; существующая логика обработки и публикации новостей остаётся самостоятельной.
- В рабочей ветке добавлено файловое логирование через `log.py`, подключённое к
  `main.py` и `mail_downloader.py`: один UTF-8 `.txt` на содержательный запуск,
  блочный формат, четыре уровня, своевременный flush и настраиваемая очистка.
  Пустые успешные проверки не создают файл. Конфиг старой версии поддерживается
  значениями по умолчанию; настройки добавлены в `config.example.py`.
- `probe/check_logging.py` проверяет журналирование и поведение конвейера
  автономно, с подменой почты и WordPress, без pytest и реальных публикаций.
  Реальную почту, WordPress и платформенную совместимость этой проверкой не
  подтверждаем. Запускать на целевой машине после установки runtime-зависимостей.
- `webui/` содержит HTML/CSS/JavaScript-макет с журналом, вкладками настроек и элементами управления Python-частью. Настоящая интеграция с Python пока **отсутствует**: запуск и события журнала имитируются, настройки сохраняются в браузере без записи в Python-конфигурацию.
- Архитектура интеграции согласована: Flask/Waitress в постоянном
  `webui_server.py`, отдельный процесс `main.py`, чтение файлов журналов и SSE.
  Backend ещё не реализован. Ближайший этап — подготовить детальный промпт для
  Codex на основе решений от 2026-10-22, затем реализовать интеграцию с
  сохранением конвейера и существующего поведения интерфейса.
- Требования к Windows 10, Debian и FreeBSD, а также решение о файле `.newsbot.disabled` для Unix зафиксированы в `gpt_context/DECISIONS.md`, но их реализация в WebUI ещё впереди.

## Согласованный следующий этап

- Рабочая ветка API: `feature/webui-api-20261022`, создана от
  `feature/run-logging-20261021` на коммите
  `baf70b36cd6828e4b60d7ace3b2dabe20061945b`. На данном этапе изменяется только
  документация; разработка API должна продолжаться в отдельной ветке, не в
  `main` и не в исходной ветке логирования.
- Состояние выполнения будет определяться по наличию и блокировке
  `.newsbot.running`; `.main.lock` остаётся постоянной защитой от второго
  экземпляра. Кнопка запуска блокируется сразу и освобождается через секунду
  после подтверждённого завершения, если новый запуск не начался.
- Журнал будет создаваться после получения `.main.lock` даже для пустой
  проверки. Полностью успешные пустые журналы удаляет сам бот в начале
  следующего запуска; API только читает. Это планируемая замена текущей
  политики отсутствия файла при пустой проверке.
- История последних 10 доступных журналов и один общий читатель новых данных
  примерно раз в 0,5 секунды; готовые строки передаются через SSE с контекстом
  блока. Целевая задержка до 2 секунд подлежит проверке.
- Сначала Windows 10 на рабочем ПК, затем Debian Linux/FreeBSD. WebUI, API и
  конвейер размещаются на одной машине. HTTPS обслуживается внешним
  Caddy/nginx/Apache, доступ нужен только из локальной сети. Конкретная служба,
  DNS, сертификат и свободные порты определяются при развёртывании; `8443`
  требованием не является.
- Предыдущие решения о `config.py`, одном администраторе и Unix-флажке
  `.newsbot.disabled` сохраняются; детали — в [DECISIONS.md](DECISIONS.md).
- При подготовке промпта нужно конкретизировать маршруты и форматы ответов,
  курсор/восстановление SSE, серверное хранение данных авторизации, пометку
  пустых журналов и защиту чтения при очень быстром повторном запуске.
  Минимальный возраст временного журнала обсуждался как возможная мера
  (например, 10 минут), но отдельное числовое требование не утверждено.
  Это детали ТЗ, а не основание менять согласованную архитектуру.

## Текущий подход к разработке

- Git-репозиторий — source of truth.
- Разработка идёт небольшими проверяемыми изменениями.
- Перед заметным изменением: сначала анализ и план, затем код.
- AI не должен делать сопутствующий рефакторинг без явного запроса.
- После изменения: review diff, тест/ручная проверка, затем commit.

## Для AI

Перед правкой:
1. Прочитать `gpt_context/ARCHITECTURE.md` и `gpt_context/DECISIONS.md`; для WebUI также `webui/README.md` и `webui/AGENTS.md`.
2. Найти реально затронутые файлы и usages.
3. Если изменение затрагивает несколько модулей — сначала предложить план.
4. Сохранять решение достаточно простым, чтобы владелец проекта мог его поддерживать.
