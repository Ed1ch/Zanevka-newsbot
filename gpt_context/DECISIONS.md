# zanevka newsbot Decisions

Короткий журнал устойчивых решений. Не записывать сюда каждую мелкую правку.

## 2026-10-07 — Репозиторий является source of truth

AI должен опираться на актуальный код и документацию в Git, а не на старые версии кода из чатов.

## 2026-10-07 — Минимальные изменения предпочтительнее широкого рефакторинга

При исправлении бага или добавлении функции не переписывать соседние модули «заодно». Большой рефакторинг обсуждается отдельно.

## 2026-10-07 — Plan -> Patch -> Review

Для нетривиальных задач сначала определить затронутые модули и риски, затем сделать ограниченный patch, после чего проверить diff и возможные регрессии.

## 2026-10-09 — Единая кодовая база для Windows 10 и Unix

Newsbot и планируемый веб-интерфейс должны поддерживать Windows 10 и Unix (прежде всего Debian Linux и FreeBSD) из одной кодовой базы. Разработка ведётся на Windows 10 с Python 3.13; совместимость с Unix предстоит проверить на целевых системах.

**Почему:** разработка выполняется на Windows, а развёртывание возможно на Unix. Поддерживать отдельные варианты приложения для каждой ОС нецелесообразно.

**Последствия:**

- Сохранять общую логику обработки писем, VK и WordPress независимой от ОС; использовать кроссплатформенные пути и файловые операции.
- Устанавливать Python-зависимости и внешний Pandoc отдельно для каждой целевой платформы.
- Настраивать запуск по расписанию вне основного Python-кода: Планировщик заданий Windows или cron на Unix (планируемый интервал — раз в 2 часа).
- Проектировать будущий веб-интерфейс с тем же требованием совместимости, пока без обязательного выбора веб-фреймворка.
- Предпочитать небольшие адресные правки, а не рефакторинг ради кроссплатформенности; до развёртывания подтвердить работу на Unix тестами.

## 2026-10-10 — Управление автоматическим запуском через файл-флажок на Unix

На Debian Linux и FreeBSD плановый запуск `main.py` остаётся во внешнем `cron` (ориентировочно раз в 2 часа). Задание cron не редактируется при обычном включении или остановке Newsbot. Вместо этого запускающий POSIX shell-скрипт перед вызовом Python проверяет файл `.newsbot.disabled` в каталоге проекта:

- Файл отсутствует — запуск разрешён; shell-скрипт запускает `main.py`.
- Файл существует — запуск пропускается с успешным завершением shell-скрипта.
- Кнопка остановки в WebUI создаёт этот файл; кнопка запуска удаляет его. Наличие и изменение файла должны проверяться с учётом прав доступа и возможных ошибок файловой системы.

**Почему:** не требуется изменять `main.py` и `config.py` ради переключателя, а также перезаписывать crontab. Работает одинаково на целевых Unix-платформах и позволяет сохранить WebUI независимым от конвейера обработки писем.

**Последствия:**

- «Запущен» означает, что автоматические запуски разрешены, а не то, что процесс `main.py` прямо сейчас выполняется. Для достоверного статуса WebUI дополнительно должен проверять наличие ожидаемого cron-задания; наличие записи в crontab само по себе не гарантирует исправность cron.
- «Остановлен» запрещает **следующие** плановые запуски; уже работающий экземпляр `main.py` не прерывается. Существующий process lock продолжает защищать от параллельной обработки.
- WebUI и cron-скрипт должны работать с одним и тем же абсолютным путём к `.newsbot.disabled`. Нужны минимально необходимые права доступа; пользователь WebUI не должен получать доступ к управлению чужими задачами cron.
- На Windows взаимодействие WebUI с Планировщиком заданий не реализуется; отображается `Windows/manual`. Проверка файла-флажка применяется только в Unix-обёртке запуска.
- Реализация и проверка поведения на Debian/FreeBSD остаются отдельным этапом; до этого запись фиксирует принятое проектное решение, но не подтверждает внедрение.

## 2026-10-22 — Один конвейер с проверкой полноты общей партии

**Статус:** согласован вариант `prelaunch → main → integrity_check → main`,
реализован в ветке `feature/batch-integrity-20261022`. Это обычные вызовы
функций в одном процессе, без перезапуска конвейера после проверки.

**Почему:** документы и изображения одной подборки могут приходить разными
письмами. Общая партия даёт сопоставление между EML; одна отсрочка позволяет
дождаться остальных писем. Существующий `main.py` сохраняется с адресными
изменениями; второй почти одинаковый конвейер не нужен.

**Модули и запуск:**

- `prelaunch.py` — единая внешняя точка запуска. Получает существующий
  системный lock `.main.lock` (`msvcrt.locking` / `fcntl.flock`) до импорта
  конвейера, удерживает до закрытия журнала и освобождает в `finally`.
  Оставшийся файл не равнозначен занятой блокировке. Прямой CLI `main.py`
  перенаправляет запуск в диспетчер; внешние Python-клиенты используют
  `prelaunch.main()`, а не внутренний `main.main()`.
- Наличие `delayed.publish` определяет режим для любого источника запуска.
  Отсутствует — `defer_if_incomplete=True`; существует — `False`.
  `main.py` погашает одноразовый флаг в начале повторного прохода под lock,
  даже при пустой проверке или последующей ошибке. Ошибка удаления останавливает
  запуск; при технической ошибке флаг заново не создаётся.
- `main.py` выполняет одну общую сборку и цикл публикации. `integrity_check.py`
  переиспользует `find_matching_images()` и возвращает данные отчёта,
  не выполняя сетевых/файловых операций и не записывая журнал.
  Отчёт считается в обоих режимах; возможность отсрочки меняет только
  реакцию на неполноту. Отдельного `first_main.py` нет.
- По уточнению от 2026-10-23 все служебные флаги и lock-файлы находятся
  в `flags/` относительно каталога проекта независимо от cwd. Каталог
  создаётся автоматически перед получением lock и исключён из Git.
  Для решения 2026-10-10 Unix-обёртка должна вызывать `prelaunch.py`
  вместо `main.py`; проверка `flags/.newsbot.disabled` остаётся во внешней обёртке.
  Управление cron и WebUI/backend этим изменением не реализуется.

**Партия и полнота:**

- При начальной проверке фиксируется весь список подходящих UNSEEN-писем
  по существующему фильтру ЗГП и порядку UID. Новые письма после фиксации
  списка ждут другого запуска. Все EML сначала скачиваются с прежними retry,
  `.part` и подтверждением SEEN; потом разбираются в общие документы/картинки.
- При одинаковом полном имени с расширением без учёта регистра оставить
  первое вложение по UID письма и порядку MIME, последующие исключить до
  сборки и записи изображений. Содержимое не сравнивать. WARNING о дубле
  сам по себе не вызывает остановку или отсрочку.
- Тексты писем не склеиваются. VK из каждого EML ищется с общим списком DOCX,
  затем результаты объединяются. Приоритет ссылки внутри DOCX сохранён.
- Отсрочка нужна при наличии хотя бы одной непривязанной картинки либо
  DOCX одновременно без сопоставленных картинок и без сопоставленного VK.
  DOCX с VK без картинок не задерживает партию. Неоднозначность сопоставления
  остаётся информационным предупреждением по прежним правилам.
- При первой неполноте: до любых загрузок медиа и публикаций вернуть всем
  письмам UNSEEN и подтвердить FLAGS сервера; только затем создать пустой
  `delayed.publish`. Завершить запуск с явным итогом WARNING об отсрочке,
  причинами и числом писем. Во всех случаях очистить временные файлы.
- Между запусками не сохраняются EML, изображения, список UID или JSON-манифест.
  При повторе заново скачиваются все подходящие UNSEEN-письма, включая новые.
  Неполнота не вызывает вторую отсрочку, непривязанные картинки перечисляются
  в журнале. Состав партии существует только в памяти текущего запуска.

**Публикация и ошибки:**

- Только при отсутствии сопоставленных картинок **и** VK использовать
  `featured_media_id` существующего `s600xu_2x.webp`. Поиск в Media API
  проверяет точное имя исходного файла и страницы результатов. Успешный ID
  кэшируется на партию; повторной загрузки и включения стандартного файла
  в галерею нет. Ошибка поиска — ошибка этой новости, остальные продолжаются.
- Для новости с VK без своих картинок отсутствие preview, ошибка его получения
  или загрузки означает пропуск этой новости, без стандартной картинки.
  Если свои картинки есть, прежнее продолжение после сбоя VK сохранено.
- После исчерпания retry неудача скачивания останавливает партию; старый
  одиночный загрузчик оставлен для совместимости, пакетный путь не пропускает
  неудачное письмо ради продолжения. Ошибки чтения Subject, разбора EML,
  подготовки материалов и записи журнала также останавливают подготовку.
  Структурные MIME-дефекты, ошибки декодирования и пустые DOCX/изображения
  не превращаются в штатную отсрочку. Флаг не создаётся.
- Уже зарезервированные письма при ошибке остаются SEEN в INBOX. Автоматического
  отката IMAP-флагов и восстановления состава партии нет, включая частичный
  сбой возврата UNSEEN или создания флага. Восстановление делает администратор.
- Ошибка отдельной новости внутри цикла публикации не прерывает остальные.
  При полном успехе все письма перемещаются в корзину; при неполном успехе
  остаются SEEN в INBOX без автоматической повторной публикации всей партии.
- Сохраняются формат журнала и своевременный flush. Добавлены режим, состав
  партии, общий отчёт, WARNING дублей и отдельный результат «публикация отложена».
  Временные EML/изображения очищаются при отсрочке, успехе и исключении;
  журнал закрывается до освобождения process lock.

**Принятые ограничения:**

- Плановый интервал — два часа. Предполагаем доставку остальных материалов
  к следующему запуску; явного сигнала окончания партии не будет.
  Остаточный риск неполной публикации принимается.
- Флаг не отсчитывает время: ручной запуск сразу включает повторный режим,
  если флаг существует. Сокращение ожидания — ответственность администратора.
- Почтовый ящик выделен Newsbot и администратору. Письма, прочитанные или
  перемещённые другим клиентом, пропускаются без восстановления.
- Кнопка Debug для сброса служебного состояния остаётся будущей задачей
  интеграции. Откат писем, сохранение состава партии и интерфейс восстановления
  почты исключены. `.main.lock` не удаляют ради принудительного разблокирования.
- `probe/check_logging.py` и `probe/check_batch.py` проверяют офлайн
  журнал, lock, общую партию, отсрочку/повтор, дубли, VK/default и ошибки.
  Они не подтверждают работу живых сервисов, реального Pandoc и целевых ОС.

## 2026-10-23 — Flask/Waitress поверх пакетного лаунчера

По явному заданию владельца реализован webui_server.py: авторизация одной
учётной записи, отдельная страница входа, CSRF, ограниченные cookie-сессии,
allowlist config.py с ревизией и атомарной заменой, история и SSE. API запускает
только отдельный sys.executable -u prelaunch.py, не импортирует конвейер ради
запуска. Это дополняет пакетное решение 2026-10-22 и не меняет его правил.

Лаунчер держит `.main.lock`, затем `.newsbot.running`, активирует один журнал
до почты. После очистки/итога закрывает журнал, снимает running и последним
освобождает общий lock. Свободный остаток running означает простой; неизвестный
статус блокирует API-запуск. Принятый запрос защищён до появления флага;
после наблюдаемого завершения выдерживается одна секунда. Выход API не убивает бот.

Обычная чистая пустая проверка получает метку после закрытия. Сам бот удаляет
её журнал в начале следующих запусков от 600 секунд (LOG_EMPTY_MIN_AGE_SECONDS).
Погашение delayed.publish исключает пустой повтор из этой классификации;
потеря метки означает обычное LOG_* хранение. Отсрочка заканчивает итоговый
WARNING точной строкой про кнопку «Запустить сейчас»; режим отдельным полем
пользовательского API не показывается.

Debug реализован пока только API: при простое под общей блокировкой удаляет
всё содержимое flags кроме существующей `.main.lock`, не следует по ссылкам,
честно возвращает частичные ошибки. Снятие disabled разрешает будущий cron;
почта/журналы/процесс не затрагиваются. Решение о будущей кнопке остаётся в силе.

Unix cron внешней POSIX-обёрткой проверяет disabled и вызывает prelaunch;
API читает только собственный crontab, не изменяет задания/часовой пояс/службы.
Windows/manual остаётся без управления Task Scheduler. HTTPS завершает внешний
прокси; Waitress — loopback:8081, prefix и IP доверенных прокси настраиваются
локально. Локальный HTTP включается явно только на loopback.

Основной WebUI не переработан: изменены источники данных и JS-обработчики.
Единственное добавление — отдельный login в исходной первой цветовой схеме.
Logout/Debug и уточнение старых подписей — отдельный UI-проход.
