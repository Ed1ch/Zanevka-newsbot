## 2026-10-09 — Единая кодовая база для Windows 10 и Unix

Newsbot и планируемый веб-интерфейс должны поддерживать Windows 10 и Unix (прежде всего Debian Linux и FreeBSD) из одной кодовой базы. Разработка ведётся на Windows 10 с Python 3.13; совместимость с Unix предстоит проверить на целевых системах.

**Почему:** разработка выполняется на Windows, а развёртывание возможно на Unix. Поддерживать отдельные варианты приложения для каждой ОС нецелесообразно.

**Последствия:**

- Сохранять общую логику обработки писем, VK и WordPress независимой от ОС; использовать кроссплатформенные пути и файловые операции.
- Устанавливать Python-зависимости и внешний Pandoc отдельно для каждой целевой платформы.
- Настраивать запуск по расписанию вне основного Python-кода: Планировщик заданий Windows или cron на Unix (планируемый интервал — раз в 2 часа).
- Проектировать будущий веб-интерфейс с тем же требованием совместимости, пока без обязательного выбора веб-фреймворка.
- Предпочитать небольшие адресные правки, а не рефакторинг ради кроссплатформенности; до развёртывания подтвердить работу на Unix тестами.

## 2026-10-10 — Управление автоматическим запуском через файл-флажок на Unix

На Debian Linux и FreeBSD плановый запуск `main.py` остаётся во внешнем `cron` (ориентировочно раз в 2 часа). Задание cron не редактируется при обычном включении или остановке Newsbot. Вместо этого запускающий POSIX shell-скрипт перед вызовом Python проверяет файл `.newsbot.disabled` в каталоге проекта:

- Файл отсутствует — запуск разрешён; shell-скрипт запускает `main.py`.
- Файл существует — запуск пропускается с успешным завершением shell-скрипта.
- Кнопка остановки в WebUI создаёт этот файл; кнопка запуска удаляет его. Наличие и изменение файла должны проверяться с учётом прав доступа и возможных ошибок файловой системы.

**Почему:** не требуется изменять `main.py` и `config.py` ради переключателя, а также перезаписывать crontab. Работает одинаково на целевых Unix-платформах и позволяет сохранить WebUI независимым от конвейера обработки писем.

**Последствия:**

- «Запущен» означает, что автоматические запуски разрешены, а не то, что процесс `main.py` прямо сейчас выполняется. Для достоверного статуса WebUI дополнительно должен проверять наличие ожидаемого cron-задания; наличие записи в crontab само по себе не гарантирует исправность cron.
- «Остановлен» запрещает **следующие** плановые запуски; уже работающий экземпляр `main.py` не прерывается. Существующий process lock продолжает защищать от параллельной обработки.
- WebUI и cron-скрипт должны работать с одним и тем же абсолютным путём к `.newsbot.disabled`. Нужны минимально необходимые права доступа; пользователь WebUI не должен получать доступ к управлению чужими задачами cron.
- На Windows взаимодействие WebUI с Планировщиком заданий не реализуется; отображается `Windows/manual`. Проверка файла-флажка применяется только в Unix-обёртке запуска.
- Реализация и проверка поведения на Debian/FreeBSD остаются отдельным этапом; до этого запись фиксирует принятое проектное решение, но не подтверждает внедрение.

## 2026-10-22 — WebUI и API через Flask/Waitress

**Статус:** архитектура согласована, реализация ещё не начата. Эта запись
дополняет решения по платформам и расписанию от 2026-10-09/10.

Постоянно работающий `webui_server.py` на Flask/Waitress будет обслуживать
WebUI и API: авторизацию, настройки, состояние процесса/расписания, ручной
запуск и журналы. Waitress работает в том же процессе и принимает HTTP.
Сервер запускает `main.py` отдельным процессом через текущий Python-интерпретатор
с небуферизованным выводом (`-u`); рабочая обработка не переносится в API.

**Почему:** один небольшой сервер связывает существующие компоненты, сохраняя
конвейер самостоятельным и пригодным для ручного запуска и cron.

**Последствия:**

- Одна кодовая база для Windows 10 / Python 3.13, Debian Linux и FreeBSD.
  Зависимости и файловое поведение проверяются на целевых ОС; эта запись
  не подтверждает уже выполненные платформенные проверки.
- Основной конфиг остаётся локальным `config.py`. API валидирует и атомарно
  изменяет только разрешённые параметры, сохраняя остальные настройки.
  Изменения используются со следующего запуска бота.
- Одна учётная запись администратора: пароль хранится сервером в виде хеша,
  авторизация использует сессионную cookie и CSRF-защиту. Секреты не попадают
  в Git, журналы API, ответы с настройками или `localStorage`; пустое секретное
  поле при сохранении означает «оставить прежнее значение».
- Управление Unix-расписанием через `.newsbot.disabled` сохраняется.
  Запрет следующих cron-запусков не останавливает текущий процесс;
  ручной запуск остаётся отдельной операцией. Windows — `Windows/manual`,
  без управления Планировщиком заданий из WebUI.
- Интеграция меняет демонстрационный запуск и источник рабочих настроек/логов.
  Существующие дизайн, темы, вкладки, плавающее окно, фильтры, масштабирование
  и режимы прокрутки сохраняются. Очистка окна журнала не удаляет файлы.

## 2026-10-22 — Состояние процесса через второй блокируемый флажок

Постоянная `.main.lock` остаётся защитой от параллельной обработки. Бот
не удаляет и не переименовывает её; наличие этого файла не является статусом
процесса. После получения основной блокировки `main.py` создаёт временную
`.newsbot.running` и удерживает её системную блокировку во время работы.

**Почему:** API должен видеть запуск через cron и после собственного
перезапуска; отслеживания только своего дочернего процесса недостаточно.

**Последствия:**

- Флажка нет — процесс не отмечен как выполняющийся; флажок заблокирован —
  бот работает; оставшийся свободный файл — остаток после завершения/аварии,
  сам по себе не означает работу. Ошибка доступа — состояние неизвестно,
  повторный запуск из WebUI временно запрещён.
- После очистки рабочих файлов, итогового сообщения и закрытия журнала бот
  закрывает и удаляет флажок. Постоянная основная блокировка освобождается
  последней. При аварии системная блокировка освобождается ОС; файл может остаться.
- API проверяет только служебный флажок, не управляет `.main.lock`.
  Проверка флажка не должна заставлять бота пропустить запуск или нарушать
  защиту конвейера. Создание/удаление флажка выполняется при удерживаемой
  основной блокировке; пути одинаковы для ручного запуска, cron и API.
- Сразу после нажатия «Запустить сейчас» кнопка блокируется, включая время до
  появления флажка. Пока бот выполняется, она заблокирована во всех панелях.
  После подтверждённого завершения выжидается 1 секунда; если начался новый
  запуск, кнопка остаётся заблокированной.
- Допускается краткая неточность состояния кнопки. Задержка не является
  межпроцессной защитой. При совпадении запросов/cron `.main.lock` допускает
  только один конвейер; второй экземпляр молча завершается, без очереди и журнала.

## 2026-10-22 — Раннее создание журнала и очистка пустых проверок самим ботом

В интеграции журнал будет создаваться сразу после получения `.main.lock`
и инициализации логирования, до проверки почты. Это **планируемая замена**
текущей политики ветки логирования, где файл появляется при подходящем письме
либо предупреждении/ошибке.

**Почему:** WebUI должен показывать и обычную проверку без новых писем;
создание и удаление файлов не должны зависеть от работающего API.

**Последствия:**

- Полностью успешная проверка без подходящих новых писем, предупреждений
  и ошибок явно помечается как пустая только после завершающей очистки,
  итогового сообщения и успешного закрытия журнала. Нельзя определять этот
  результат лишь по отсутствию обработанных писем или наличию файла.
- Завершённые пустые журналы удаляет сам бот в начале следующего запуска,
  после получения основной блокировки. API не удаляет файлы и не подтверждает
  их прочтение для завершения `main.py`; ожидание API в боте не вводится.
- Журналы с обработкой писем, предупреждениями, ошибками или незавершённым
  запуском сохраняются по обычным правилам `LOG_*`. Посторонние файлы и
  активный журнал не удаляются.
- Если API отсутствует, последующие запуски всё равно выполняют очистку.
  Если новых запусков нет, последний временный журнал может остаться.
- При очень быстром повторном запуске опрос раз в 0,5 секунды не гарантирует
  чтение файла до его удаления. В ТЗ нужно конкретизировать защиту этого окна;
  минимальный возраст файла обсуждался как возможная мера, без утверждённого
  числового значения. Ни мгновенное удаление, ни фиксированная задержка кнопки
  сами по себе не дают гарантии доставки.
- Ошибки импорта до инициализации логирования и ошибки создания файла могут
  остаться только в stderr. Для собственного дочернего процесса API должен
  сообщать раннюю диагностику отдельно от обычного файлового потока, маскируя
  секреты. Для внешнего запуска ранний stderr остаётся диагностикой cron/ОС;
  автоматическое появление такого вывода в WebUI не обещается.

## 2026-10-22 — История файлов и один общий поток SSE

При подключении панели API загружает последние 10 доступных журналов, затем
передаёт новые данные через SSE. Один общий читатель сервера примерно каждые
0,5 секунды проверяет файлы и раздаёт новые строки всем открытым панелям.
Целевая задержка отображения — до 2 секунд; подтверждается при проверке
готовой интеграции, а не предполагается по одному значению интервала.

**Почему:** для ожидаемых 1–3 панелей достаточно одного читателя без
дублирования файлового опроса на каждый браузер.

**Последствия:**

- API читает только добавленные байты, сохраняя позицию для каждого файла.
  Неполная строка/часть UTF-8 символа остаётся до следующего чтения; передаётся
  каждая законченная строка сразу, без ожидания конца сводного блока.
- Заголовки и строки с табуляцией сохраняют общий уровень и принадлежность
  к блоку. Метки времени берутся из журнала, а не из часов браузера.
- История и живой поток согласуются через курсор; переподключение не должно
  давать пропуски или дубли в пределах сохранённых данных. Буферы ограничены;
  при недоступном курсоре требуется явная повторная синхронизация.
- Читатель учитывает появление новых файлов, очистку старых и перезапуск API.
  Если файлов меньше десяти, показываются имеющиеся. Уже показанный текст
  остаётся в панели после удаления временного файла.
- На Windows API открывает файл на короткое чтение и закрывает его.
  Временно занятый при удалении файл переносится на следующую очистку;
  обработка почты не останавливается ради его удаления.
- API только читает журналы: не вызывает `log.setup()` и не запускает
  очистку хранения. Обычные сообщения не передаются одновременно из файла
  и stdout, чтобы не создавать дубли.

## 2026-10-22 — HTTPS вне API и развёртывание в локальной сети

WebUI, `webui_server.py` и модули Newsbot работают на одной физической машине.
Сначала это рабочий ПК с Windows 10; последующее развёртывание возможно на
Debian Linux или FreeBSD. Доступ к интерфейсу нужен только в локальной сети.

**Почему:** HTTPS и выбор внешнего веб-сервера относятся к окружению
развёртывания и не должны привязывать API к конкретной ОС или службе.

**Последствия:**

- Waitress принимает обычный HTTP на `127.0.0.1` и настраиваемом внутреннем
  порту. Внешний Caddy/nginx/Apache принимает HTTPS и направляет в него
  запросы WebUI, API и SSE. Waitress сам по себе уже является HTTP-сервером;
  для локальной проверки допускается прямой HTTP без внешнего прокси.
- При наличии подходящей службы используется она. Caddy на Windows и Apache
  на FreeBSD — допустимые варианты; Caddy не является обязательной
  зависимостью приложения. Перенос меняет конфигурацию развёртывания,
  а не реализацию API.
- Внутренний порт выбирается при реализации как изменяемое значение
  по умолчанию; его доступность проверяется при развёртывании. Внешние
  порты и маршрутизация задаются в Caddy/nginx/Apache. Уже работающий
  сервер может обслуживать несколько доменов на одном HTTPS-порту.
  Номер `8443` не является требованием.
- Домен вроде `newsbot.zanevkaorg.ru`, DNS и сертификат на соответствующее
  имя настраиваются при развёртывании. Размещение на том же HTTPS-домене
  под префиксом вроде `/newsbot/` тоже допускается; приложение должно
  корректно учитывать внешний адрес и префикс.
- API доверяет сведениям о внешнем HTTPS только от настроенного прокси.
  Настройки прокси должны обеспечивать своевременную передачу SSE.
- Локальный/самоподписанный сертификат с браузерным исключением допустим.
  Установка корневого сертификата не является обязательным требованием;
  конкретный способ доверия выбирается при развёртывании. Обязательной
  зависимости от покупки сертификата или публичного доступа нет.
