# zanevka newsbot Decisions

Короткий журнал устойчивых решений. Не записывать сюда каждую мелкую правку.

## 2026-10-07 — Репозиторий является source of truth

AI должен опираться на актуальный код и документацию в Git, а не на старые версии кода из чатов.

## 2026-10-07 — Минимальные изменения предпочтительнее широкого рефакторинга

При исправлении бага или добавлении функции не переписывать соседние модули «заодно». Большой рефакторинг обсуждается отдельно.

## 2026-10-07 — Plan -> Patch -> Review

Для нетривиальных задач сначала определить затронутые модули и риски, затем сделать ограниченный patch, после чего проверить diff и возможные регрессии.

## 2026-10-09 — Единая кодовая база для Windows 10 и Unix

Newsbot и планируемый веб-интерфейс должны поддерживать Windows 10 и Unix (прежде всего Debian Linux и FreeBSD) из одной кодовой базы. Разработка ведётся на Windows 10 с Python 3.13; совместимость с Unix предстоит проверить на целевых системах.

**Почему:** разработка выполняется на Windows, а развёртывание возможно на Unix. Поддерживать отдельные варианты приложения для каждой ОС нецелесообразно.

**Последствия:**

- Сохранять общую логику обработки писем, VK и WordPress независимой от ОС; использовать кроссплатформенные пути и файловые операции.
- Устанавливать Python-зависимости и внешний Pandoc отдельно для каждой целевой платформы.
- Настраивать запуск по расписанию вне основного Python-кода: Планировщик заданий Windows или cron на Unix (планируемый интервал — раз в 2 часа).
- Проектировать будущий веб-интерфейс с тем же требованием совместимости, пока без обязательного выбора веб-фреймворка.
- Предпочитать небольшие адресные правки, а не рефакторинг ради кроссплатформенности; до развёртывания подтвердить работу на Unix тестами.

## 2026-10-10 — Управление автоматическим запуском через файл-флажок на Unix

На Debian Linux и FreeBSD плановый запуск `main.py` остаётся во внешнем `cron` (ориентировочно раз в 2 часа). Задание cron не редактируется при обычном включении или остановке Newsbot. Вместо этого запускающий POSIX shell-скрипт перед вызовом Python проверяет файл `.newsbot.disabled` в каталоге проекта:

- Файл отсутствует — запуск разрешён; shell-скрипт запускает `main.py`.
- Файл существует — запуск пропускается с успешным завершением shell-скрипта.
- Кнопка остановки в WebUI создаёт этот файл; кнопка запуска удаляет его. Наличие и изменение файла должны проверяться с учётом прав доступа и возможных ошибок файловой системы.

**Почему:** не требуется изменять `main.py` и `config.py` ради переключателя, а также перезаписывать crontab. Работает одинаково на целевых Unix-платформах и позволяет сохранить WebUI независимым от конвейера обработки писем.

**Последствия:**

- «Запущен» означает, что автоматические запуски разрешены, а не то, что процесс `main.py` прямо сейчас выполняется. Для достоверного статуса WebUI дополнительно должен проверять наличие ожидаемого cron-задания; наличие записи в crontab само по себе не гарантирует исправность cron.
- «Остановлен» запрещает **следующие** плановые запуски; уже работающий экземпляр `main.py` не прерывается. Существующий process lock продолжает защищать от параллельной обработки.
- WebUI и cron-скрипт должны работать с одним и тем же абсолютным путём к `.newsbot.disabled`. Нужны минимально необходимые права доступа; пользователь WebUI не должен получать доступ к управлению чужими задачами cron.
- На Windows взаимодействие WebUI с Планировщиком заданий не реализуется; отображается `Windows/manual`. Проверка файла-флажка применяется только в Unix-обёртке запуска.
- Реализация и проверка поведения на Debian/FreeBSD остаются отдельным этапом; до этого запись фиксирует принятое проектное решение, но не подтверждает внедрение.

## 2026-10-22 — Диспетчер запуска и однократная отсрочка общей партии писем

**Статус:** принятое направление разработки; в этой записи описано планируемое
поведение. На момент принятия решения код ветки по-прежнему обрабатывает письма
по одному через `main.py`; новые стартовые модули ещё не реализованы.

**Что решили:**

- Ввести единую точку запуска `prelaunch.py`. Она получает существующую
  системную блокировку `.main.lock`, выбирает один пайплайн и удерживает
  блокировку до его полного завершения, включая очистку файлов и закрытие
  журнала. Наличие файла `.main.lock` само по себе не означает занятость:
  существующую реализацию через `msvcrt.locking` / `fcntl.flock` переносим
  без замены на проверку существования файла.
- Если `delayed.publish` отсутствует, запускать `first_main.py`; если
  существует — `main.py`. Выбор выполняется после получения process lock.
  Предпочтителен вызов выбранного модуля в том же Python-процессе, чтобы время
  жизни блокировки совпадало со временем жизни обработки.
- `main.py` становится обычным пакетным пайплайном с публикацией.
  `first_main.py` — его архитектурная копия с дополнительной проверкой
  полноты и возможностью одной отсрочки. Широкий рефакторинг `main.py`,
  общий базовый класс или универсальная система пресетов не требуются.
  Предметные функции остаются в существующих модулях.
- Для обоих пайплайнов в начале проверки фиксировать список подходящих
  UNSEEN-писем с темой, соответствующей существующему фильтру ЗГП. Скачать
  и извлечь материалы всех этих писем, собрать общие `documents` и `images`,
  затем сформировать новости. Письма, пришедшие после фиксации списка,
  обрабатываются в другом запуске. Публикация и загрузка медиа в WordPress
  начинаются только после подготовки всей партии.
- Границы текстов писем сохранять: VK-ссылки из писем искать отдельно в каждом
  EML с общим списком документов, затем объединять результаты. Сохранять
  приоритет ссылки внутри DOCX и существующие правила сопоставления файлов.
  Проверку полноты выполнять после определения сопоставленных VK-ссылок,
  до любых загрузок медиа.
- `first_main.py` откладывает всю партию, если есть хотя бы одна картинка без
  соответствующего документа либо DOCX без сопоставленных картинок **и без
  сопоставленной VK-ссылки**. DOCX с VK-ссылкой без картинок отсрочку не вызывает.
  При полном сопоставлении первый пайплайн сразу публикует новости.
- При штатной отсрочке создать пустой `delayed.publish`, вернуть письмам
  текущей партии UNSEEN, подтвердить изменение флагов на IMAP-сервере, удалить
  временные EML и изображения. Между запусками не хранить содержимое писем,
  список UID или JSON-манифест. UID нужны только в памяти текущего запуска
  для существующих IMAP-операций.
- В следующем запуске снова найти и скачать все подходящие UNSEEN-письма,
  включая отложенные и новые. `main.py` не выполняет повторную отсрочку
  из-за неполного сопоставления; непривязанные картинки перечисляет в журнале.
  Новые письма не начинают ещё один период ожидания для этой проверки.
- Для новости без сопоставленных изображений и без сопоставленной VK-ссылки
  использовать существующий файл `s600xu_2x.webp` из медиатеки как
  `featured_media_id`. Найти его по точному имени, повторно не загружать
  и не добавлять в галерею; результат поиска можно кэшировать на один запуск.
  Отсутствие доступного ID — ошибка соответствующей новости, остальные
  продолжают обрабатываться.
- Для DOCX без картинок, но с VK, стандартную картинку не подставлять.
  Ожидаемое поведение при невозможности получить или загрузить VK preview —
  ошибка этой новости и переход к следующей, без отсрочки всей партии.
  Это отдельная точечная корректировка текущего кода: сейчас
  `process_vk()` возвращается при отсутствии preview, а исключения VK
  перехватываются с продолжением публикации. Не распространять новое правило
  автоматически на другие случаи обработки VK.

**Почему:** изображения и документы одной подборки могут приходить разными
письмами. Общая партия позволяет сопоставить их между EML, а одна отсрочка даёт
время для доставки оставшихся материалов. Отдельный диспетчер позволяет позже
добавлять стартовые модули или пресеты без расширения обязанностей `main.py`.

**Необходимые правила реализации:**

- `delayed.publish` — одноразовое разрешение следующего запуска `main.py`.
  Погашать его под process lock при передаче управления повторному пайплайну.
  Ошибка удаления флага останавливает запуск. Пустая проверка также расходует
  флаг, чтобы он не переключал посторонние будущие партии в повторный режим.
  При технической ошибке повторного прохода флаг заново не создаётся.
- Возврат UNSEEN допустим только при штатной отсрочке до любых загрузок медиа
  и публикаций. При невозможности создать флаг или подтвердить возврат UNSEEN
  результат считается технической ошибкой, а не успешной отсрочкой:
  по возможности откатить уже выполненные изменения флагов и убрать
  `delayed.publish`, явно сообщить о неполном откате. Изменение состояния IMAP
  и локального файла не является одной атомарной операцией; аварийное
  завершение процесса между ними не имеет гарантии автоматического
  восстановления без дополнительного постоянного состояния.
- После retry ошибка скачивания, ошибка разбора EML или конфликт вложений
  останавливает подготовку всей партии до публикации; `delayed.publish`
  не создаётся, UNSEEN для автоматического повторения не возвращается.
  Уже зарезервированные письма остаются SEEN в INBOX по прежней модели
  обработки ошибок. Временные файлы очищаются и при исключении.
- Это требует адресных изменений не только `main.py`: существующий
  `download_news_email()` после ошибки скачивания переходит к следующему
  письму; конфликт одинаковых имён пока не проверяется, изображения могут
  перезаписываться; разбор MIME не гарантирует исключения на любом
  повреждённом EML. Проверки и сигнал остановки партии нужно добавить
  явно. Точные повторы «имя + содержимое» объединять, одинаковое имя
  с разным содержимым считать конфликтом до записи изображений на диск.
- Ошибка отдельной новости внутри этапа публикации не останавливает обработку
  остальных. Перед первой загрузкой медиа все письма партии должны иметь
  подтверждённый SEEN. При полном успехе все письма партии перемещаются
  в корзину; при неполном успехе остаются SEEN в INBOX без автоматической
  повторной публикации всей партии.
- Журнал содержит выбранный пайплайн, состав партии в рамках запуска,
  общий отчёт сопоставления и явный результат «публикация отложена» со списком
  причин. Штатную отсрочку отличать от технической ошибки и успешной
  публикации, сохраняя существующий формат заголовков и строк продолжения.
- После реализации все внешние запуски — ручные, cron и будущий API —
  направлять через `prelaunch.py`; прямой запуск внутренних пайплайнов
  не должен обходить общую блокировку. В Unix-обёртке из решения
  2026-10-10 проверка `.newsbot.disabled` сохраняется, а целевой запуск
  меняется с `main.py` на `prelaunch.py`. Пути к файлам-флажкам и lock-файлу
  считаются от каталога проекта, независимо от рабочего каталога cron.
- При реализации обновить проверки в `probe/`: текущая
  `probe/check_logging.py` обращается к lock-функциям `main.py` и
  проверяет продолжение после ошибки скачивания/VK, поэтому часть ожиданий
  должна измениться согласно этому решению.

**Принятые ограничения и последствия:**

- Расписание — один запуск раз в два часа. Предполагаем, что к следующей
  проверке оставшиеся письма уже доставлены. Явного признака окончания партии
  от отправителя не будет; остаточный риск неполной публикации принимается.
- Источник запуска для выбора пайплайна передавать не нужно: достаточно
  `delayed.publish`. Сам флаг не отсчитывает два часа. Ручной запуск при
  установленном флаге сразу выберет повторный пайплайн и может сократить
  ожидание; временную паузу обеспечивает внешнее расписание.
- Без постоянного списка UID партия следующего запуска определяется заново
  по UNSEEN. Если другое приложение или человек пометит отложенные письма
  прочитанными либо переместит их, бот не восстановит прежний состав.
- Две версии конвейера допустимы как осознанный компромисс:
  общие исправления сборки/публикации нужно проверять в обоих пайплайнах,
  чтобы они не расходились по поведению за пределами проверки отсрочки.
